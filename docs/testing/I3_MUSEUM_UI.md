# I3 — Museum UI foundation

## Scope and boundaries

The Museum UI uses installed uGUI, TextMeshPro, and the Input System. No new package, external asset, network dependency, AR behavior, demonstration, or Android build is introduced. The catalog remains the source of exhibit identifiers, titles, and historical text. Bootstrap and ARExperience are outside this task; open Museum directly to inspect this UI.

## Structure

- `Assets/IARA/Content/MuseumCatalog.cs`: read-only JSON DTOs and basic schema/identifier checks.
- `Assets/IARA/Application/MuseumState.cs`: category selection and expanded exhibit state; no UI or scene dependencies.
- `Assets/IARA/Presentation/`: serialized uGUI/TMP components, safe-area handling, responsive filter grid, and Museum screen binding.
- `Assets/IARA/Presentation/Prefabs/`: reusable PavilionFilter and ExhibitCard assets generated by the Editor builder.
- `Assets/IARA/Editor/MuseumUiBuilder.cs`: explicit, repeatable scene/prefab generation using installed TMP essentials. It preserves an existing MuseumScreen and existing prefab edits, refuses dirty Museum scenes or conflicting EventSystems, and retains the Museum scene GUID.
- `Assets/IARA/Tests/Editor/`: catalog-state tests plus an integration test that enters Play Mode and invokes the actual UI button callbacks.

The UI references the existing local catalog TextAsset through a serialized field. It does not modify or synchronize JSON files. Layer assembly definitions keep application/content code independent from presentation; Editor code stays under an Editor folder.

## Interaction and visual conventions

The portrait layout has a collection header, All exhibits plus three pavilion filters, a vertical ScrollRect, expandable cards, and Collection / Back to top / About controls. The About view returns to the same collection state. Collection resets the filter and scroll position; filtering resets scrolling while expansion persists for each exhibit during the current scene session.

Canvas Scaler uses a 1080×2400 reference and width matching. Filter cells adapt to the available safe-area width in two columns. Main controls are 144 reference units high (48 pixels at 360-pixel portrait width); body text is 48 reference units. The dark palette uses light text and mint selection, with a textual Selected indication so selection is not conveyed by color alone. This is not a claim of screen-reader support or completed accessibility certification.

Historical descriptions are currently blank in JSON. Cards display the UI-only messages “Description pending editorial review” and “Historical details are not yet available in this draft catalog.” These messages are not historical content. `View in AR / coming later` is deliberately disabled: no AR scene transition, marker tracking, or placement is connected. English pavilion labels are UI translations keyed to existing category IDs; exhibit titles remain unchanged.

## Generate and inspect

Save work before changing scenes. In the installed Editor:

1. Run **IARA → Museum → 1. Import bundled TMP essentials**. This imports only resources already shipped with installed uGUI, including its supplied font/license resources; it does not download a package.
2. Run **IARA → Museum → 2. Build Museum UI**.
3. Open `Assets/IARA/Scenes/Museum.unity` directly and enter Play Mode.
4. In Test Runner, run `Iara.Tests.MuseumUiTests` in EditMode. Its integration test enters and exits Play Mode.

For headless runs, close the Editor using this project first. Use the actual installed Unity executable with `-batchmode -nographics -buildTarget Android -projectPath <project>`. Run `-executeMethod Iara.Editor.MuseumUiBuilder.ImportFonts` **without `-quit`**: package import is asynchronous, and the completion callback verifies the font before exiting. In a separate run, use `-quit -executeMethod Iara.Editor.MuseumUiBuilder.Build`. For tests add `-runTests -testPlatform EditMode -testFilter Iara.Tests.MuseumUiTests -testResults <ignored-local-results-path>`; omit `-quit` so the test runner owns shutdown.

## Implementation decisions and lifecycle

MuseumScreen initializes when Museum starts, reads its serialized TextAsset, creates four filter instances and eight card instances from the two prefabs, then binds them to MuseumState. Filtering activates/deactivates existing cards instead of rebuilding their identities. Expansion is keyed by exhibitId in memory, persists across filters, and resets when this scene session is destroyed; there is no disk persistence.

Selecting a pavilion resets the scroll position. Collection selects All and returns to the top; Back to top only moves the scroll. About temporarily hides the catalog and returns to its prior state. The scene does not implement Bootstrap → Museum or Museum → ARExperience navigation.

The Editor builder is an explicit setup tool, not a runtime UI generator. It saves the initial scene hierarchy and reusable prefab assets. It rejects an unsaved Museum scene or an existing conflicting EventSystem and leaves an existing MuseumScreen/prefab setup alone. This makes generation safe to repeat but does not provide an automatic migration system for later UI design changes.

## Interpretation of completion

I3 completes the coded Museum UI foundation and its automated checks. It does not establish full acceptance of CAT-01 through CAT-05, offline operation on a provisioned phone, Android deployment, AR behavior, or verified educational content. A missing JSON description is presented explicitly rather than filled with invented history. No performance, memory, screen-reader, or device-usability acceptance result is available.

For review, first open Museum directly in the Editor, perform the GUI checklist, then inspect the serialized references on MuseumScreen and the two prefabs. Keep any follow-up fixes scoped to the observed issue. Subsequent scene-flow or AR implementation requires a separate authorized task.

## Portrait visual correction — 2026-11-20

The developer reported defects in Device Simulator using **Punch Hole Center, 1440×3088, portrait**: filters outside the safe area's right edge, horizontally clipped expanded card text, oversized footer buttons, and insufficient separation between scrolling content and fixed navigation. The header was reported correctly positioned and its safe-area/scaler configuration was preserved.

### Root cause and changes

uGUI's HorizontalOrVerticalLayoutGroup clamps child widths to their reported minimum widths. GridLayoutGroup and wrapped TMP content can therefore push a parent beyond the available width unless their layout inputs are bounded. The grid's earlier resize callback did not break that minimum-width feedback. Fixed-height LayoutElements also left flexibleHeight unspecified, allowing the navigation's HorizontalLayoutGroup to supply a positive flexible height to the Page layout.

- Layout-controlled children now explicitly report minWidth/preferredWidth 0 and flexibleWidth 1, allowing the parent's available width to determine wrapping instead of expanding the page or card.
- Fixed-height helpers explicitly set flexibleHeight 0. Only flexible regions consume surplus height; the footer and its buttons remain 144 reference units tall. Navigation no longer forces child-height expansion.
- FilterGridSize participates in the layout cycle through ILayoutSelfController and computes cell width from current width, padding, spacing, and column count, without repeatedly assigning an unchanged size.
- Card ContentSizeFitter remains vertical-only. Content stays horizontally stretched at the viewport top; horizontal scrolling is disabled.
- MuseumScreen rebuilds the serialized Page layout root so ancestor widths are resolved before wrapped text heights and scroll bounds.
- The Editor builder creates the corrected configuration for new UI and provides **IARA → Museum → 3. Apply portrait layout correction** for existing I3 assets. This targeted operation updates Museum and ExhibitCard in place, preserves their GUIDs, and rejects unsaved scenes or Play Mode. It does not delete/recreate the UI or change header text, font sizes, safe-area logic, or CanvasScaler values.

### Regression evidence

The added PortraitLayoutStaysInsideSafeArea test was run before the fix: it failed at 1440×3088 with navigation height **774**, expected **144 ± 1**. This exposed a real gap in the original I3 tests: they measured text height without asserting horizontal bounds, footer height, or footer/list separation.

After applying the correction, the entire MuseumUiTests suite passed: **4 passed, 0 failed**, process exit 0. A final rerun after strengthening safe-area assertions also passed all four tests. The new Play Mode test covers 1440×3088, 1080×2400, and 480×800 equivalents, each with full safe area and synthetic 3.5% edge insets, across all four filter states: **24 layout states**, with visible cards expanded. It asserts filter bounds, viewport/navigation/button containment within the safe area, card/text horizontal containment, expanded text height, footer/button height, a usable remaining viewport, non-overlap with navigation, content taller than the viewport, and preserved 216-unit header height within the safe area. Existing interaction/state/invalid-content tests also passed.

These tests use a temporary world-space canvas and injected geometry, not measured Punch Hole Center cutout dimensions. The exact Device Simulator profile has not been visually rechecked by the agent; real pixel rendering and touch remain manual. No Android build or physical-device test was run.
